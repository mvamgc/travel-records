# ADR-0010: Maps — a self-hosted OpenStreetMap basemap, saved areas, and locations set by the owner

- **Status:** Accepted
- **Date:** 2026-10-24
- **Resolves:** where the map view (REQ-015, REQ-065) gets its map data, and how it works offline; HLD §11 ADR-0010
- **Changes requirements:** adds REQ-087 to REQ-091, and a non-goal (place search and place names)
- **Amends:** [ADR-0001](0001-resumable-media-upload.md) (an original whose location the owner chose is cleaned before it becomes `available`); [ADR-0005](0005-toolchain-and-deployment.md) (CloudFront serves the map file under `/tiles/`); [ADR-0006](0006-public-media-location.md) (originals lose their embedded location once the owner edits it; the in-place overwrite extends to photos)

## Context

The map view plots the user's geotagged items (REQ-015), and members see the same map for an album or travel (REQ-065). Public pages have no map (ADR-0006). The markers come from IndexedDB, so they work offline like everything else. The map underneath them, with its roads, coastlines and place names, has to come from somewhere.

These facts constrain the design:

- **Travellers are often offline exactly where the map matters.** A place they didn't look at while online shows blank, unless its map was saved beforehand.
- **Map requests reveal where the user is looking,** which is mostly where their photos were taken. Whoever serves the map sees those requests.
- **OpenStreetMap's own tile servers forbid offline use.** Their policies prohibit downloading tiles in advance, and the OpenStreetMap Foundation blocks apps that do. Commercial map services charge per request, need an API key in the client, and restrict what apps may keep offline, each in its own terms.
- **OpenStreetMap data is open** (Open Database License). Anyone may host it, serve it and keep it offline, with attribution. Protomaps publishes daily builds of a complete world basemap as one PMTiles file: vector tiles for zoom levels 0 to 15, about 139 GB.
- **A PMTiles file is read with byte-range requests.** A small index locates each tile. Tiles are stored in Hilbert-curve order, so the tiles of one area at one zoom level sit in a few contiguous runs, and the low zoom levels come first.
- **The Cache API can't store partial (`206`) responses,** which is what range requests return.
- **Photos chosen through Safari's file picker on iOS often lose their location.** WebKit strips it unless the user turns location on in the picker's options. Users need a way to set it by hand.
- **Members see original files with their metadata** (REQ-065). A location the owner removes from an item would still be inside its original file.

Decision drivers, in priority order:

1. The map works offline wherever the user prepared for it, and never blocks the rest of the app.
2. No third party learns which places a user looks at.
3. Few requests on high-latency links, and downloads that resume after a drop.
4. Map data never crowds out the user's own content in storage (REQ-021).
5. Little infrastructure and cost.

## Decision

### 1. MapLibre GL JS draws a vector map

- The map view uses **MapLibre GL JS** (BSD licence), which draws vector tiles with WebGL. Labels stay sharp at any zoom and on high-density screens. Past the data's last zoom level (15), it enlarges the vector shapes instead of blurring images.
- It is the app's only sizeable JavaScript dependency: about 1 MB minified, 275 KB compressed. The service worker caches it with the app shell, so it's available offline, but it loads only when the map view first opens.
- Leptos drives it through a thin JavaScript shim reached with `wasm-bindgen`: create the map, set the markers, move the camera, report taps.
- **Markers** are a GeoJSON source built from IndexedDB: the user's own items, or an album's or travel's entries with their metadata copies (ADR-0008). MapLibre clusters them. Tapping a cluster zooms in, and tapping a marker opens the item with its local preview. Markers never need the network.
- The map style, the label fonts for common scripts and the icons are part of the app's files. Fonts for other scripts are fetched when first needed and stored like viewed tiles (decision 3).
- The map shows "© OpenStreetMap contributors", as the licence requires.

### 2. We host the map data ourselves, as one file

- The Protomaps basemap build sits in its own S3 bucket. CloudFront serves it under `/tiles/` on the app's own origin (ADR-0005 decision 5), cached, with range requests, and without sign-in. The tiles are public map data, like the app's own files, so guests get the map too.
- The client reads the file with the `pmtiles` JavaScript library (8 KB compressed): the header and root index in one 16 KB request, then index pages and tiles as needed. Index pages are kept in IndexedDB, so a new area costs its extra round trips once.
- There is no server code for maps: no tile function, no API keys, and no fees beyond CloudFront and S3. Storing the world costs about $3 a month.
- **Updates are rare and manual.** A new build gets a new file name, and the app's map configuration points to it, so a device never mixes index offsets from two builds. Tiles already stored keep working, and are replaced in the background when the user views them online.
- The dev environment uses a small extract of a few test areas, made with `pmtiles extract`, instead of the whole world.
- Map requests reach only our CloudFront, never a third party, and aren't logged.

### 3. What works offline

The client stores tiles in IndexedDB by zoom, column and row. It serves them to MapLibre through a custom protocol, so the map doesn't know whether a tile came from the network or from the device. There are three kinds of stored tiles:

| Kind | What | When it's stored | When it's removed |
|---|---|---|---|
| **World overview** | the whole world at zoom levels 0 to 5 | Once, the first time the map opens online. The low zoom levels come first in the file, so this is a single range request. | Never |
| **Viewed places** | the tiles the map loaded while online | As they're viewed | Least recently used first, beyond a size cap |
| **Saved areas** | an area the user chose, at every zoom level | When the user saves it (decision 4) | When the user deletes it |

Offline, where a tile isn't stored, the map shows the most detailed stored level for that place, the world overview at worst, and always the markers (REQ-087).

Map data never pushes out user content. When storage runs low (REQ-021), viewed places are removed first, and saved areas only after the user confirms (REQ-089).

### 4. Saved areas

- The user frames an area on the map and chooses **Save for offline**. For a travel with geotagged items, the app suggests the area around them. For a planned travel, the user frames its destination.
- Before downloading, the app shows the area's **exact size**, read from the file's index, and refuses areas above a size limit (REQ-088).
- **Download:** at each zoom level, the area's tiles form a few contiguous runs in the file. The client merges runs separated by small gaps and fetches each with one range request, so an area takes tens of requests instead of thousands. Each run is stored as it arrives. After a drop, the download continues with the runs not yet stored.
- Downloads run in the background, only while text and previews have nothing waiting (lanes 1 and 2), and share the connection with originals. The user sees progress and can pause or cancel.
- Settings list the saved areas with their sizes, and the user can delete any of them (REQ-089).

### 5. Owners can set, move or remove an item's location

- From an item they own, the user opens **Location** and places a pin on the map, moves it, or removes the location (REQ-090). This is an edit of the item's geotag field like any other: saved offline, synced in lane 1, with conflicts handled per ADR-0004. Album and travel entries get the new location through their metadata copies (ADR-0008).
- Once the owner has edited an item's location, the only location the item has is the one they chose. The item records this, and the server removes the location embedded in its original file:
  - an original uploaded after the edit is cleaned before it becomes `available` (ADR-0001 decision 6);
  - an original already stored is replaced by a cleaned one.
- Cleaning overwrites the location fields in place, as ADR-0006 decision 3 does for public video copies: nothing is re-encoded, and no offsets move. This extends that code to photo formats: EXIF and XMP in JPEG and HEIC.
- Copies of the original that members already downloaded keep the old location. Previews never had it (REQ-067).

## Considered options

1. **Leaflet with raster tiles.** A smaller library. Rejected: raster tiles need a rendering server or a third-party provider, look blurry on high-density screens unless they are four times larger, and need more zoom levels stored per saved area to stay sharp.
2. **OpenStreetMap's public tile servers.** Free. Rejected: their policies forbid prefetching and offline use, and apps that do it get blocked.
3. **A commercial map service** (MapTiler, Stadia Maps, Mapbox, Amazon Location Service). No map data to host. Rejected:
   - the service sees which places users look at;
   - fees per request, and an API key in the client;
   - offline use restricted, differently in each service's terms;
   - another origin for the Content Security Policy.
4. **Serving standard tile URLs (`/{z}/{x}/{y}`) through a Lambda,** as Protomaps' own AWS setup does. Any map client works, and the service worker could cache tiles like other files. Rejected: a function with cold starts on the map's hot path, and a saved area would take thousands of requests instead of tens.
5. **Storing tiles with the service worker's Cache API.** Rejected: it can't store the partial responses of range requests. IndexedDB also keeps all local data in one store with one storage budget (REQ-019, REQ-021).
6. **Shipping a region's map with the app.** Rejected: tens to hundreds of megabytes, and no region suits every traveller.
7. **Saving the map around the user's items automatically.** Rejected (user decision): it uses data in the background, and the POC can't tell Wi-Fi from roaming.
8. **Changing only the geotag field when the owner edits a location.** Rejected: members who open the original would still find where it was taken, so removing a location wouldn't hide it.
9. **Place search and place names** (geocoding). Not in the POC: nothing requires it, and it needs either a service that sees every query or a large offline index.

## Consequences

- **Good:**
  - the map works offline in saved areas and recently viewed places, the world overview is always there, and markers never need the network;
  - a saved area downloads in tens of resumable requests, and the user sees its exact size first;
  - no third party sees where users look, and there are no API keys or per-request fees;
  - no server code for maps: one file in S3 behind the existing CloudFront;
  - owners can fix locations, and a removed location is gone from the original too.
- **Bad:**
  - MapLibre is a sizeable JavaScript dependency in a Rust app, reached through a shim, and it needs WebGL 2;
  - a 139 GB file to store and to replace by hand; the map is as old as the build;
  - saved areas can take hundreds of megabytes on the device;
  - the map file is public, so anyone can download it at our expense. It's open data anyway. Without CORS headers, other sites' pages can't use it, but scripts can;
  - cleaning stored originals is new server work, for photo formats as well as video;
  - originals that members already downloaded keep the old location;
  - no place search or place names.
- **Follow-ups:**
  - a map LLD: the custom protocol and tile store, the size cap and eviction, choosing an area, the download queue, markers and clustering, the location picker;
  - media LLD: cleaning originals, including which functions do it and how the item records that its owner chose the location;
  - CDK: the maps bucket and the `/tiles/*` behaviour, plus a script that copies a build into S3;
  - parameter values in `docs/ear.md`.

## Parameters

Initial values, to be pinned in `docs/ear.md`:

| Parameter | Initial value | Basis |
|---|---|---|
| World overview zoom levels | 0 to 5 | Lowered if the spike measures it above its budget. |
| World overview size budget | 30 MB | Downloaded once, possibly over a poor link. |
| Viewed-places cache | 100 MB | Several cities' worth of browsing. |
| Saved-area zoom levels | 0 to 15 | The basemap's last level; MapLibre enlarges beyond it. |
| Saved-area size limit | 500 MB | Keeps one area from filling a phone. |
| Gap merged in area downloads | 32 KB | A few wasted kilobytes cost less than a round trip on a slow link. |

## Validation spike

1. Sizes from a current build: the world overview at zoom levels 0 to 4, 5 and 6; saved areas for a large city and for a 100 km square, up to zoom 14 and 15; and the number of range requests each takes after merging.
2. MapLibre in a Leptos page through the shim, with tiles served from IndexedDB through the custom protocol, in Safari, Chrome and Firefox and in the app installed on iOS and Android. Offline, a missing tile shows the most detailed stored level.
3. Range requests through CloudFront to a 139 GB S3 object: latency with a cold and a warm cache, and whether index pages are cached at the edge.
4. Thousands of clustered markers on a mid-range phone.
5. Hundreds of megabytes of tiles in IndexedDB on iOS: whether the browser keeps them, with and without persistent storage (REQ-054).
6. In-place cleaning of photo originals: JPEG and HEIC from iPhones and Android phones, added to ADR-0006's test corpus and checked with `exiftool`.
